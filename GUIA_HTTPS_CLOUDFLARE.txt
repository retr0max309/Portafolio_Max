PORTAFOLIO MAX: HTTPS EN ORACLE CLOUD Y URL DE CLOUDFLARE
=========================================================

1. OBJETIVO

Mostrar el portafolio por una URL gratuita de Cloudflare sin comprar un dominio,
y demostrar que la VM de Oracle realmente atiende HTTPS en el puerto 443.

URL pública: https://portafolio-max.maximilianoturderacolque.workers.dev/
Origen HTTPS: https://portafolio.168-138-148-187.sslip.io/
IP de la VM: 168.138.148.187

Recorrido de una solicitud:
Navegador -> HTTPS de Cloudflare -> Worker -> HTTPS:443 de Oracle ->
Nginx -> http://127.0.0.1:8080 -> contenedor Next.js -> NestJS/Supabase.

La URL workers.dev pertenece a Cloudflare. sslip.io es un servicio DNS gratuito
que convierte el nombre con la IP incorporada en 168.138.148.187. Necesitamos
ese nombre para emitir un certificado verificable para el servidor de Oracle.
No se compra un dominio ni se usa la dirección sslip.io como URL de presentación.

2. QUÉ SE CONFIGURÓ EN LA VM Y POR QUÉ

2.1. Se conservó Ubuntu 24.04, la VM, la VCN, la subred y la IP pública creadas
     con Terraform. Las reglas de OCI e iptables ya permiten TCP 80 y TCP 443.
     Abrir un puerto solo permite tráfico; además debe existir un proceso que
     escuche y responda en él.

2.2. Se cambió compose.prod.yml para publicar Next.js únicamente en
     127.0.0.1:8080 de la VM. Así los visitantes no llegan directamente al
     contenedor. NestJS sigue accesible solo dentro de la red de Docker.

2.3. Se instaló Nginx en Ubuntu. Nginx escucha el puerto 80 para la validación
     del certificado y la redirección HTTP -> HTTPS, y el puerto 443 para TLS.
     Nginx reenvía las solicitudes al contenedor Next.js en 127.0.0.1:8080.
     La IP directa todavía responde por HTTP como vía de diagnóstico.

2.4. Certbot obtuvo de Let's Encrypt un certificado para
     portafolio.168-138-148-187.sslip.io mediante el desafío HTTP-01 en el
     puerto 80. La clave privada queda solo en /etc/letsencrypt de la VM.
     El temporizador certbot.timer renueva el certificado; el hook de despliegue
     recarga Nginx cuando Certbot lo renueva.

2.5. El script scripts/configure-https-vm.sh reúne la migración y deja la
     configuración reproducible. Se ejecutó en la VM con sudo. El script
     scripts/remote-release.sh se actualizó para comprobar el puerto local
     8080 y el origen HTTPS después de cada publicación.

3. QUÉ HACE CLOUDFLARE

La cuenta gratuita tiene el subdominio
maximilianoturderacolque.workers.dev. El Worker llamado portafolio-max usa
la URL estable portafolio-max.maximilianoturderacolque.workers.dev.

El archivo cloudflare/worker.mjs recibe solicitudes GET, POST y otras,
conserva la ruta, los parámetros y el cuerpo de la petición, y las envía al
origen HTTPS de Oracle. Esto permite que el formulario siga funcionando.
Las redirecciones del origen se reescriben a la URL de Cloudflare.

El archivo cloudflare/wrangler.toml fija el nombre del Worker y la dirección
HTTPS del origen. Cloudflare aloja el Worker, pero la aplicación Next.js y la
API NestJS siguen ejecutándose dentro de los contenedores de la VM.

4. AUTOMATIZACIÓN EN GITHUB ACTIONS

Siguen existiendo solo dos archivos de workflow:
  .github/workflows/all-tests.yml
  .github/workflows/terraform-vm.yml

En dev se ejecutan tipos, pruebas unitarias, de integración, tres pruebas
del Worker, compilación y E2E. En main se repiten esas pruebas, Terraform
verifica la infraestructura, Docker publica las imágenes en Docker Hub,
OCI Run Command despliega la versión en la VM, Actions comprueba el origen
HTTPS, publica el Worker con Wrangler y comprueba la URL de Cloudflare.

La variable de GitHub CLOUDFLARE_ACCOUNT_ID identifica la cuenta. El secreto
CLOUDFLARE_API_TOKEN permite que Wrangler publique el Worker. El token se
crea en Cloudflare con la plantilla "Edit Cloudflare Workers", limitado a la
cuenta, y se guarda en GitHub Settings -> Secrets and variables -> Actions.
Nunca debe pegarse en un archivo del repositorio ni en esta guía.

5. CÓMO COMPROBARLO MANUALMENTE DESDE POWERSHELL

Resolver el nombre del origen:
  Resolve-DnsName portafolio.168-138-148-187.sslip.io -Type A
Resultado esperado: 168.138.148.187.

Comprobar la redirección y el certificado de Oracle:
  curl.exe -I http://portafolio.168-138-148-187.sslip.io/
  curl.exe -I https://portafolio.168-138-148-187.sslip.io/
Esperado: HTTP 301 hacia https y luego HTTP 200. curl.exe verifica el
certificado HTTPS por defecto, así que no uses la opción -k.

Comprobar la URL pública de Cloudflare:
  curl.exe -I -A "PortafolioMax-Healthcheck/1.0" https://portafolio-max.maximilianoturderacolque.workers.dev/
Esperado: HTTP 200. Cloudflare puede rechazar agentes automáticos genéricos
en workers.dev; por eso se envía un User-Agent descriptivo.

Abrir la URL de Cloudflare en un navegador, revisar los proyectos y enviar
un mensaje de contacto. Después revisar contact_messages en Supabase.

6. COMPROBACIONES DENTRO DE LA VM

Desde la carpeta del proyecto en PowerShell:
  $sshKey = 'C:\Users\NITRO\Documents\Proyecto-Sistemas III\TareasFinales\ssh-key-2026-10-01.key'
  $vm = 'ubuntu@168.138.148.187'
  ssh -i $sshKey $vm 'sudo ss -ltnp | grep -E ":(80|443|8080) "'
  ssh -i $sshKey $vm 'systemctl is-active nginx certbot.timer'
  ssh -i $sshKey $vm 'sudo certbot certificates'
  ssh -i $sshKey $vm 'sudo docker compose --env-file /opt/portafolio/.env.production -f /opt/portafolio/compose.prod.yml ps'

Esperado: Nginx escucha 80 y 443; Docker publica el frontend solo en
127.0.0.1:8080; nginx y certbot.timer están activos; API y web están sanos.

7. LÍMITES DE ESTA SOLUCIÓN DE PRÁCTICA

La IP de Oracle fue asignada a la VM. Si la VM se reemplaza y cambia la IP,
habrá que actualizar el nombre sslip.io, solicitar otro certificado y cambiar
ORIGIN_URL en cloudflare/wrangler.toml. La URL workers.dev puede conservarse.
La disponibilidad de sslip.io y workers.dev depende de esos servicios.

No pruebes HTTPS usando la IP numérica directamente: el certificado fue
emitido para el nombre sslip.io, y el navegador verifica esa coincidencia.
